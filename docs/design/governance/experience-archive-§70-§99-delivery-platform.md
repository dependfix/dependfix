## 七十、M42 归档批次经验沉淀（测试断言真实性 / 外部工具语义 / 视觉基线连带 / 交付纪律）

> **批次**：M42 修复交付正确性 + 平台能力与体验补强（2026-10-11 归档）。以下 9 条已按 L1 / L2 / L3 三层收敛，规范落点与检查点矩阵行同步登记。

### 1. 交互断言的点击目标必须与组件事件绑定一致（e2e 弱断言与 flaky 的共同根因）

- **现象**：断言「点击表头排序」时点了表头单元格，而组件把点击绑定在单元格**内部**的按钮上 → 排序从未触发；断言却仍可能通过——接口默认按创建时间倒序返回，用例按序插入的数据使首行恰为「期望端点值」。
- **手法**：① 断言前先确认事件绑定元素（读组件模板：单元格只挂 `aria-sort`，触发器是内部按钮）；② 目标态必须**只能由目标行为产生**（用排序属性硬锁，未排序态为 `none` 必然失败）；③ 三态控件逐次点击并**等待属性回写**（异步渲染下立即读会读到旧值 → 多点击 → 状态过冲）。
- **落点**：[testing.md §6.5](../../standards/testing.md)（交互断言补充）+ 检查点矩阵行。

### 2. 与外部工具语义对齐的判定须用该工具权威实现逐形态实测

- **现象**：`.gitignore` 幂等判定的首版实现按书写直觉把「行中 `#`」当行内注释剥离，与 git 实际语义不符（git 仅把行首 `#` 当注释）→ 假命中 → 漏追加 → 报告目录可能随提交入库（**安全方向回归**）。
- **手法**：列形态清单（**含反例**）→ 用工具权威判定命令逐形态实测 → 与实现双向比对；等价类扩展倾向保守（宁可多报不可漏判）。
- **落点**：[development.md §5.1.40](../../standards/development.md)（新条款）+ 检查点矩阵行。

### 3. 改动页面的视觉基线重建含「以该页为背景」的连带面

- **现象**：页头加一个按钮 / 改 flex → 整页基线失配（预期）；**另有弹窗内浮层的视口级基线同样失配**（其取景包含该页背景）。
- **手法**：改动页面后列出该页相关的全部基线（整页 + 视口 + 元素级），逐个判断是否需重建；重建用 `--update-snapshots=all` 并连跑两遍验证幂等；无视觉守卫的页面显式登记。
- **落点**：[testing.md §6.7](../../standards/testing.md)（扩展）+ 检查点矩阵行。

### 4. 验证同进程服务时不得用同步子进程调用

- **现象**：用 `spawnSync` 拉起被测工具去验证「本进程内的拦截代理」→ 同步调用阻塞事件循环 → 代理无法 accept → 记录为空 → 误判「代理未生效」。
- **手法**：改用异步 `spawn` + 等待退出；配合**同环境反例对照**（旧配置再跑一次）证明代理确实被使用且修复确实生效。
- **落点**：[testing.md §6.10](../../standards/testing.md)（新条款）+ 检查点矩阵行。

### 5. ESM 接线断言用「部分 mock + 委托真实实现」

- **现象**：ESM 下无法用 spy 断言「A 以某实参调用 B」；整体 mock B 又会破坏依赖 B 真实行为的既有用例。
- **手法**：`vi.mock` + `importOriginal` 保留其余导出、仅包装目标函数（记录实参后**委托真实实现**）；实参容器由 `vi.hoisted` 提供，用例断言后于 `beforeEach` 清空。
- **落点**：[testing.md §6.6](../../standards/testing.md)（扩展）+ 检查点矩阵行。

### 6. 删除公共导出前必须全仓 grep（含全部测试目录）

- **现象**：删除工具函数导出时只查了源码与同目录测试，漏掉集中测试目录 → `typecheck` 报 TS2305。
- **手法**：不带路径限定的全仓检索 + 区分代码引用与文档描述性文本；测试文件按「同目录 + 集中目录」双份核对；核验引用面时注意 `rg -r` 是替换陷阱（输出被替换成假象）。
- **落点**：[development.md §5.1.39](../../standards/development.md)（新条款）+ 检查点矩阵行。

### 7. 同批同源断言必须全仓一次改净

- **现象**：同一批在多个文件写入同一 `file:line` 断言，修复时只改了其中一处 → 审计判「同源残留」。
- **手法**：修复任一处后用旧值全仓复核；跨文件同源写入是该规则的另一个变体。
- **落点**：[planning.md §4.4 第 13 条](../../standards/planning.md)（扩展）+ 检查点矩阵行扩展。

### 8. 阶段状态口径翻转的同步面含各文档速查表

- **现象**：阶段启动 / 归档时把「暂无进行中阶段」翻转为「Mxx 进行中」，漏改某文档的速查表 → 自相矛盾，且批次记录中「口径已同步」的声明失实。
- **手法**：列出全部承载位置（待办速查表 / 路线图指针 / 各文档速查表 / 首页里程碑）逐处同步。
- **落点**：[documentation.md §6](../../standards/documentation.md)（扩展）+ 检查点矩阵行。

### 9. 入口脚本（PID 1 / 子进程编排）用真实 shell + PATH 桩做脚本级测试

- **现象**：root 降权 / 子进程看护 / 信号处理等编排逻辑难被 TS 单测覆盖，但属可靠性关键路径。
- **手法**：`sh` 直驱脚本 + 经 `PATH` 注入桩命令（`id` / `sleep` / `date`）重塑环境（降权分支、即时退避、时间快进）；断言基于输出流与进程存活探测；Windows 用 `describe.skipIf` 跳过。
- **落点**：[testing.md §6.10](../../standards/testing.md)（新条款）+ 检查点矩阵行。

## 七十一、M43 归档批次经验沉淀（收窄改动语义 / 注入时机 / 门禁与脚本单测 / 覆盖面声明）

> **批次**：M43 PR Check 能力补强 + 运行时可靠性与工程治理（2026-10-14 归档；含阶段期间 caomei-ui `0.6.0` 升级回归插队热修）。**准入依据**：各条满足 [experience-archive.md 文件头](./experience-archive.md) 准入标准之一（可执行方法论尚未迁移到规范 / 决策需溯源 / 同类问题复现 ≥ 2 次 / 工具与环境陷阱），落点见各条目末行。以下 7 条已按 L1 / L2 / L3 三层收敛，规范落点与检查点矩阵行同步登记。

### 1. 「收窄 / 跳过」类改动必须先穷举被跳过步骤产物的消费者

- **现象**：为省成本 / 消除假失败而**整段跳过**某流水线步骤，该步骤的产物却同时被别处当判据 → 无关路径语义退化：零告警仓库的「处理成功」信号原由收尾验证链的 `verificationPassed` 承载，跳过使「健康零告警仓库 + 真实失败仓库」的多仓运行由 exit 1 退化为 exit 2（恰好是该批次要消除的误归因形态）。
- **手法**：按**字段级**穷举被跳过步骤产物的全部消费者；把跳过后的判据空洞显式补上（新增信号，或跨用例不变量锁定）；审计此类改动先问「被跳过的步骤是否还在别处产出判定依据」。
- **落点**：[development.md §5.1.41](../../standards/development.md)（新条款）+ 检查点矩阵行。

### 2. 可注入 composable 的缺省实现必须在 setup 期解析 setup-only 依赖

- **现象**：为可测性引入 `useXxx(deps)` 时，缺省实现写成延迟求值的缺省参数 → `useI18n()` 在事件处理期被调用（setup-only composable）→ 抛错被 handler 的 try/catch 吞掉 → **三条分支（合并 / 成功 / 失败）全部静默失效**；注入桩的单测不复现、`typecheck` / `lint` 均 0 报错。
- **手法**：缺省分支用 `deps.x ?? resolveXxx()`，`resolveXxx()` 在 setup 期求值一次并闭包持有；事件期只调 event-safe 全局（`$fetch` / `navigateTo`）。检出手段是**既有 e2e 全量复跑**（失败用例表现为超时而非断言失败）。
- **落点**：[development.md §5.1.42](../../standards/development.md)（新条款）+ 检查点矩阵行。

### 3. 门禁 / 脚本类单测的两个 mock 语义陷阱

- **现象**：① 早返回分支只写 `process.exit(0)` 时，测试环境（`process.exit` 被 mock）会继续落到后续逻辑 → 「删除该分支副作用」的 mutation **存活**（自检阶段一度漏杀）；② 为 `scripts/**` 写单测时，夹具里写入会被该脚本判定的字面量（规划编号形态）→ 门禁在**源码层**命中自己；夹具 token 若与其所在行被拼接成一行，`it(...)` 作为测试名单元不做引号感知 → 必命中。
- **手法**：早返回处 `process.exit` **兼** `return`；夹具用运行时拼接构造 token（不写字面量），或依赖「行尾注释提取会跳过字符串字面量」的特性。
- **落点**：[testing.md §6.11](../../standards/testing.md)（新条款）+ 检查点矩阵行。

### 4. 规范 / 文档的「覆盖面」声明必须带作用对象限定

- **现象**：声明「push 侧全部 4 处推送调用点」时未限定作用对象 → repo-wide 阅读被理解为「零遗漏」，而 `scripts/**` 的发布辅助脚本同样执行 `git push`（其作用对象是工具自身而非被修复仓库）；审计据此追问并判 warning。
- **手法**：覆盖面声明限定**作用对象**并显式列出**不适用面**；声明前先 `rg` 穷举并按作用对象分组。
- **落点**：[documentation.md §6](../../standards/documentation.md)（扩展）+ 检查点矩阵行。

### 5. 文档示例与实现不一致时优先补实现侧的容忍

- **现象**：文档给出的摘要行示例（裸 `→ <target>`）实现未捕获（正则要求 `→ 详见/已迁移至` 前缀）→ 按文档字面书写时 `target` 恒为 `null`；同形问题还表现为历史区条目整段未被识别为「已蒸馏条目」。
- **手法**：若该形态属**既有文档已声明的约定**，在实现侧扩展容忍并补测（本次顺带使历史区条目开始携带 target）；把文档改窄会把已存在的既有数据形态判为「不支持」。
- **落点**：[documentation.md §6](../../standards/documentation.md)（同一扩展的第二点）+ 检查点矩阵行。

### 6. complement-stash 多 commit 隔离的两个操作性陷阱

- **现象**：① `git add -N`（intent-to-add）的新文件让 `git stash push` 报 `Entry … not uptodate. Cannot merge` → 隔离失败；② 隔离脚本无 EXIT trap 时，commit 被 commitlint 拒绝后 `set -e` 在 `git stash pop` 之前退出 → 补集改动**滞留 stash**（本次实测踩中一次，靠 `git stash list` + `git stash pop` 人工恢复）。
- **手法**：stash 前对 intent-to-add 文件先 `git reset -- <path>` 退回未跟踪；隔离脚本用 `trap restore EXIT` 保证失败路径也恢复补集。
- **落点**：[git.md §3.7.1](../../standards/git.md)（扩展）+ 检查点矩阵行扩展。

### 7. 语义变更必须连带同步同源声明（JSDoc / 注释 / 同源断言）

- **现象**：`hasGitChanges` 改为「非仓库返回 false」后，同函数族的门禁 JSDoc 仍写「回滚失败（如非 git 目录）追加 `ROLLBACK_FAILED`」——与新守卫（非仓库在回滚之前短路）矛盾；审计判 warning（属该批次 AC 明列的同步项）。
- **手法**：语义变更时按**同源面**扫描并同步：实现旁的 JSDoc / 注释、引用该语义的测试名与测试注释、以及同族函数的交叉引用；「被替换的旧触发条件」是最高频漏点。
- **落点**：[development.md §5.1.41 / §5.1.42](../../standards/development.md) 对应的两条检查点矩阵行（本条不单独开条款），并以本条 7 的现象清单作为「同源面」枚举模板。

## 七十二、入口脚本信号处置顺序与「本地不可复现偶发红」的取证路径

> **批次**：M44 阶段期间插队热修（entrypoint 双进程信号处置顺序竞态，按插队例外清单第 3 类「CI 主链路阻塞」+ 用户授权处置）。**准入依据**：④ 工具 / 环境陷阱（缺陷只在本机不可复现的调度下出现）+ ② 决策需溯源（「就绪行严格晚于处置安装」属容器停止语义的约定）。落点见各条目末行。

### 1. 就绪行必须晚于信号处置安装（观测方同步点唯一性）

- **现象**：容器入口脚本先打印「进程 pid」就绪行、后安装 TERM / INT 转发 trap → 以该行同步发停止信号的观测方（容器编排 / 健康检查 / 行为测试）可能落在窗口内，内核按默认处置终止 PID 1：退出码为 signal 终止而非约定值，看护循环与 worker 亦短暂失去父进程。
- **手法**：把「对外可观测的就绪声明」与「进程编排已就绪」绑定为同一顺序不变量——先装 trap，再启动子进程，最后打印就绪行；主进程尚未启动时补 fail-safe 退出（防吞掉停止信号后照旧启动）。
- **落点**：[platform.md §10.6](../../standards/platform.md#_10-6-队列执行进程隔离-独立-worker-进程)（严格约束 + 已知边界 ⑤⑥）+ 检查点矩阵行 + L1 源码顺序断言（`apps/platform/docker/entrypoint.test.mjs`）。

### 2. 偶发红的取证路径：重跑定性 → 负例标定 → 静态守卫固化

- **现象**：同一 commit、同一 runner 镜像下同一用例时而通过时而报 signal 终止；本机定向探针与全量测试均不复现——「本地不可复现」本身不能作为「无缺陷」的依据。
- **手法**：① 先**重跑失败 job 定性**（同镜像同 commit 重跑即绿 → 判定偶发而非回归，避免误改）；② 再按机制假设做**负例标定**放大窗口（把 trap 放回就绪行之后 + 用绝对路径 `sleep`，绕过 PATH 桩）→ 复现出与 CI 完全一致的退出形态；③ 对只在特定调度下出现的竞态，用**源码顺序断言**（L1）替代不可稳定复现的运行期断言；④ 运行期断言携带 `signal` 字段与失败消息，使同类失败一次定位。
- **落点**：[testing.md §6.10](../../standards/testing.md)（扩展：就绪行同步点断言 + 桩命令屏蔽陷阱）+ 对应检查点矩阵行扩展。

## 七十三、M45 阶段归档批次：插队容量治理、测试库隔离与双路径护栏

> **批次**：M45 阶段归档 + 沉淀（运行可靠性与交付链收口，2026-10-15 ~ 2026-10-19；阶段期间插入 **9 批**临时任务）。**准入依据**：② 决策需溯源（插队容量再平衡为用户 2026-10-19 明确裁定）+ ③ 同类问题已复现（插队、测试库污染、双路径护栏均 ≥ 2 次）+ ④ 工具 / 环境陷阱（视觉库污染、内核日志归因、gh 超时）。落点见各条目末行。

### 1. 插队不占编号 ≠ 不占预算：阶段容量必须再平衡

- **现象**：M45 原计划 6 原子，阶段期间累计插入 9 批临时任务（生产故障 / CI 双红 / 安装失败取证 / 交付正确性等），执行窗口与验证预算被反复挤压；「追加临时待办（不占阶段条目编号）」的标记口径只解决编号与位置，未约束**执行容量**。
- **手法**：批准插队后先做容量影响评估（插队工作量 + 剩余原子 + 验证 / 审计预算）；命中阈值（累计 ≥ 3 批 / 插队 ≥ 原计划 50% / 窗口内无法完成验证）时**移出优先级最低的原子到 backlog**（保留 8 要素并标注移出原因），不得以压缩验收、跳过 Review Gate 或缩短审计替代；结论写入 todo 阶段头、插队条目与 archive 批次记录三处，归档时统计「插队批次 / 再平衡移出」数量。
- **落点**：[planning.md §3.1.1](../../standards/planning.md#_3-1-1-插队后的阶段容量再平衡-hard-requirement-2026-10-19) + [review 检查点矩阵](../../../.github/skills/code-reviewer/references/code-quality-checklist.md#规范条款-review-检查点矩阵-严格约束逐条挂接) 新增行。

### 2. 审计 / 探针不得向共享测试库写入业务数据

- **现象**：审计子智能体为验证「仓库表单 → API → 列表」链路，在视觉测试库（`apps/platform/data/visual.sqlite`，gitignored）创建了 3 个 `parp3-*` 仓库；随后视觉套件的 `/repos` 与弹窗类**视口级**基线出现与代码无关的整表差异（15067 / 56733 px），排查成本高。
- **手法**：视觉库与 e2e 库均只允许 fixtures 写入——审计 / 探针一律只读或复制到 `/tmp` 操作；本地视觉复跑前核对「库内仓库集合 == fixtures 集合」，出现整表差异时先查残留而不是重建基线；清理按主键逐条删除（CASCADE 带走关联行）。
- **落点**：[testing.md §6.7](../../standards/testing.md#_6-7-视觉回归-截图识别层-apps-platform)（测试库隔离与污染核验）+ 检查点矩阵行扩展 + backlog 候选「视觉套件测试库残留非 fixtures 仓库导致基线失配」。

### 3. 内核 SIGKILL 日志与业务日志按时间戳对齐，是 OOM 归因的最强证据

- **现象**：安装失败长期被归为「环境性失败」，无法区分出网抖动与资源瓶颈；内核 `journalctl -k` 的 kill 时间与引擎日志行**同秒对齐**，进程名为 `MainThread`（Node 主线程），才把猜测变成因果链。
- **手法**：排 OOM / 被杀类问题先取内核日志 + 进程名 + RSS，再谈应用层；`exit code -1` 表示被信号杀死（不是普通失败），需与 signal 一并渲染；证据写入失败发生点，避免超时截断丢掉收尾日志。
- **落点**：[development.md §5.1.44](../../standards/development.md)（子进程终止证据）+ [§5.1.47](../../standards/development.md)（失败证据回退与就地留痕）。

### 4. 顶格文件上的增强以「替换既有语句」落地

- **现象**：`repo-fix.ts` 受 `max-lines: 800` 约束（注释与空行计入），改动前已 799/800；新增语句必然越线。
- **手法**：把三处 `progress.failed++` 改写为 `recordUpgradeFailure(...)`（计数 + 日志成对），净增仅 import 一行即完成行为增强；代价是零余量，已在触发条件命中时先拆文件（`repo-fix-finalize.ts`）。
- **落点**：[todo-archive.md §M45.2](../../plan/todo-archive.md)（该候选的处置记录）+ `repo-fix-finalize.ts`（拆分落点）+ 本条环境注记。

### 5. 归档切片按 H2 边界，骨架重写保留表结构

- **现象**：按行号切片把下一个 `##` 标题一并纳入，产生重复 / 空壳段；`todo.md` 速查表重建时丢表头与分隔行，产物渲染 0 `<table>` 而 `check:docs` / `lint:md` / `docs:build` 全绿不报。
- **手法**：切片按 `^##` 边界定位；骨架化重写表格必须保留表头 + 分隔行，并以产物 `<table>` 计数兜底；里程碑收口同步面显式包含 `docs/index.md` 首页卡片。
- **落点**：[planning.md §4.4 第 23/24 条](../../standards/planning.md#_4-4-大批量归档批次操作规范) + 检查点矩阵行。

### 6. 「未配置路径逐字段等价」需要逐字段冲突 fixture

- **现象**：聚合层引入「配置关注集走新路径 / 未配置沿用快照」双路径后，`overallStatus` / `checkRunId` 两个 null 分支的 mutant 在既有用例下存活。
- **手法**：造一个「快照 5 个派生字段全部与 signals 派生态冲突」的用例，断言存储值等于快照值；逐字段冲突才能让任一分支改走派生即失败。
- **落点**：[development.md §5.1.46](../../standards/development.md) + 检查点矩阵行。

## 七十四、M47 归档批次经验沉淀（数据前提 / 停机语义 / 门禁与提交卫生 / 周报豁免）

### 1. 统计项必须核实数据列的生产写入方

- **现象**：周报「豁免」最初按 `ScanResult.fixStatus='converged'` 统计，但该列自 per-alert 模型起只写 `not-tried`（修复结果不回写），生产恒 0；单测直接种 converged 行造成假绿；经全仓写入点核对后改为 `RunSummary.alertsConverged`。
- **手法**：新增统计 / 去重 / 降级前先 `rg` 目标字段全部写入点；无法证实写入方时改用已落库的汇总字段，或把边界登记为残余。
- **落点**：[development.md §5.1.48](../../standards/development.md) + 检查点矩阵行。

### 2. 去重前提会随语义演进失效，「读不到」不得静默截断

- **现象**：验证链记录口径从「计划命令」改为「实际执行命令」后，原「首写胜出」前提失效；读取目标仓库 workflow 时只取前 N 个文件会让被丢弃项的关键语义漏判并产出「一致」假阳。
- **手法**：去重键 / 缓存前提与语义同批复核（改并集或失效键）；「无法读取 / 超限」整体降级并在文案写明原因，不静默截断。
- **落点**：[development.md §5.1.48](../../standards/development.md) + 检查点矩阵行。

### 3. 判据单点化要连适配层、停机与记账位置一起收口

- **现象**：环境性失败判据收敛后，lockfile 链「未启动即取消」抛普通 Error 被「stderr 空 → 环境性」吞掉；子步骤停机只停本步，调用方仍进入下一链路；`addSkipped` 放函数尾部被提前 return 整段跳过。
- **手法**：适配层先把取消 / 超时 / 空输出转成同形错误；停机状态以返回值向上传导；一次性记账前移到分区处。
- **落点**：[development.md §5.1.49](../../standards/development.md) + 检查点矩阵行。

### 4. 跨端哨兵与枚举必须镜像常量并等值断言

- **现象**：构建版本 `unknown` 在 server 与前端各写裸字面量，`unknown` 判定两份实现；任一端口径漂移都会让「未知」显示与判定分叉。
- **手法**：前端导出镜像常量（或共享包导入），server 测试断言两侧相等；「是否未知」收敛到单一纯函数。
- **落点**：[development.md §5.1.50](../../standards/development.md) + 检查点矩阵行。

### 5. 豁免限流时要同步排除共享计数查询

- **现象**：周报逐封投递写入的 `sent` 行虽豁免自身限流，却仍计入共享每小时上限；一次周报即可把平台事件 / 安全告警全部挤成 `skipped_throttled`。
- **手法**：豁免分支与计数查询同批修改（`category: Not('weekly_digest')`），并补「周报发送后常规类别仍可发送」用例。
- **落点**：[development.md §5.1.51](../../standards/development.md) + [platform-notification.md §7.3](platform-notification.md) + 检查点矩阵行。

### 6. lint-staged 的 `updateIndex` 会把未暂存文档带进 feat commit

- **现象**：即使业务 glob 已移除裸 `git add`，lint-staged 仍按任务前后 `git diff` 差异重暂存；M47.4 / M47.5 两次把 `docs/standards/platform.md`、`docs/design/...` 吞进 feat commit。
- **手法**：拆批前把未暂存文档 `git stash` / 还原到 HEAD；每组 `git add` 后核对 `git diff --cached --name-only`，提交后 `git show --stat HEAD` 复核；误入时 soft reset 重新分组。
- **落点**：[git.md §3.7.1](../../standards/git.md) + 检查点矩阵行。

### 7. 脚本管道状态与 mutation 证据可复核性

- **现象**：`cmd | tail` 后接 `|| fail` 在 dash（无 `pipefail`）下是死代码；mutation 工件只写「N/N 击杀」无法复核，审计要求逐项文件 / md5 / 失败用例名。
- **手法**：拆分「捕获输出（带失败判定）」与「解析输出」；mutation 工件记录文件、变异前 md5、失败用例名与复现命令，还原后 md5 核对。
- **落点**：[testing.md §6.10 / §6.8](../../standards/testing.md) + 检查点矩阵行。

### 8. 官方 Node 基础镜像的工具链口径

- **现象**：官方镜像默认 corepack shim 会回源下载 pnpm 覆盖镜像内版本；node-gyp 默认回源 headers；pnpm 11 只认 `pnpm_config_*` 前缀。
- **手法**：钉 pnpm 前先移除 shim；受限网络设 `npm_config_nodedir`；切 registry 时同时导出两种前缀，并在构建期断言版本基线。
- **落点**：[platform.md §10.1](../../standards/platform.md) + 检查点矩阵行。

## 七十五、M49 归档批次经验沉淀（发布通道 / 发布物自检 / 事实取证 / 验收对账 / 版本引用）

> **批次**：M49 0.6.0 发版清障 + 阶段期间 3 批追加临时待办（2026-10-25 ~ 2026-10-29）。**准入依据**：④ 工具 / 环境陷阱（本地发布通道绕过门禁、元数据硬编码）+ ② 决策需溯源（发布前安全告警门禁分级）+ ③ 同类问题已复现（发布事实多方取证、版本引用回填）。落点见各条目末行。

### 1. 发布通道必须与安全门禁同源

- **现象**：发布前安全告警门禁只接在 `release.yml`，本地备用通道 `pnpm release:publish --otp` 无门禁调用；0.6.0 即经该通道发布，门禁脚本存在但未执行。
- **手法**：任一路径发布前都跑同一门禁（脚本内调用或显式 `--skip-security` 并记录理由）；备用通道步骤在发布指南中与 CI 通道同列。
- **落点**：backlog「本地发布通道不执行发布前安全门禁」+ [security.md §5.9](../../standards/security.md)。

### 2. 发布物自检要实测元数据，help 正常不等于版本正确

- **现象**：`meta.version` 硬编码 `0.1.0`，0.6.0 发布后 `npx dependfix@0.6.0 --version` 仍返回 0.1.0；`report-only --help` 完全正常，发布后验若只看 help 会漏判。
- **手法**：发布后验逐项实测 `--version` / 安装路径 / 帮助输出；版本类元数据一律从 `package.json` 读取（发布产物与源码两种布局都要覆盖）并补一致性用例，禁止硬编码。
- **落点**：[backlog.md](../../plan/backlog.md)「0.6.0 发布物 `--version` 报 0.1.0」+ `packages/cli/src/cli/runner.ts` 的 `resolveCliVersion` 双布局读取。

### 3. 发布事实以四方取证，脚本 exit 0 不作证据

- **现象**：`release:publish` 成功后 tag 创建、npm 发布时间与 GitHub Release 各自独立；Docker 镜像推送要等 `docker.yml` 的 QA + 多架构构建，滞后约 8 分钟。只看脚本退出码会把「已发布」写早。
- **手法**：归档前按 npm registry（版本 + 发布时间）、`git tag`、GitHub Release、Actions run 四方复核，并记录时点；口径不一致（如镜像仍在推送）如实写「执行中 / 待复核」。
- **落点**：[release-1.0-readiness.md G3.8](./release-1.0-readiness.md#_2-门槛与判定-g1-g8) + [backlog.md](../../plan/backlog.md) Docker tag 复核条目。

### 4. 「已完成」要与验收标准逐条对账，未达标项转 backlog

- **现象**：M49.5 五项验收中 `--version`、3 连绿窗口、Docker tag health 三项在归档时点未完全达成；若按「阶段已完成」笼统收口，会把未验证项写成已通过。
- **手法**：归档正文按 AC 逐条标注 ✅ / ◐ / ❌ 并附证据；未达标项转 backlog 并写恢复条件（发布 0.6.1 / 后续 push 累计 / run 收尾复核），不修改验收口径。
- **落点**：[release-1.0-readiness.md](./release-1.0-readiness.md#_2-门槛与判定-g1-g8) 的 G1 / G4 未达标标注 + [backlog.md](../../plan/backlog.md) 0.6.1 / 3 连绿窗口条目。

### 5. 发布后必须回填用户可见文档的版本引用

- **现象**：Action 示例在 M49.4 按当时已发布的 `v0.5.0` 对齐，0.6.0 发布后仍有 10 处旧版本（`quick-start` / 首页 / README 4 处 + 设计文档 4 处 + en-US 镜像 2 处）；文档门禁不校验「引用的 tag 是否为最新」。
- **手法**：发布收口清单增加「示例版本引用回填」一项，发布后 `rg '@v[0-9]'` 全量复核；版本引用属发布事实，随发布批次同批更新。
- **落点**：[documentation.md §6](../../standards/documentation.md) 状态口径同步面 + 检查点矩阵。

## 七十六、M50 归档批次经验沉淀（配置单位 / overrides 语义 / 兜底副作用 / 注入式标定 / 标定选点 / typecheck 覆盖 / 周期任务状态机）

> **批次**：M50 通知可信度收口 + 阶段期间 1 批插队（CI prod 依赖审计阻断，2026-10-29 ~ 2026-10-30）。**准入依据**：④ 工具 / 环境陷阱（`minimumReleaseAge` 单位、模态内 `Escape` 副作用、闭包赋值被流分析窄化）+ ② 决策需溯源（`overrides` 语义订正、周报重试上界与退避口径）+ ③ 同类问题已复现（视觉标定选点、周期任务并发进入均 ≥ 2 次）。落点见各条目末行。

### 1. 配置项的单位必须查官方文档，不能按直觉读

- **现象**：`pnpm-workspace.yaml` 的 `minimumReleaseAge: 60` 被当成「60 天」，据此新增 7 条 `minimumReleaseAgeExclude` 去「放行安全补丁」；实测该配置单位是**分钟**（默认 1440 = 1 天），补丁版本（11 天 / 8 天龄）根本不违窗口，exclude 整块多余且治理口径错误（审计 R1 deep 判 blocker）。
- **手法**：给配置加数值前先查官方文档确认单位与默认值；若结论是「安全补丁被成熟窗口挡住」，先做最小对照实验（同配置下不带 exclude 能否解析到补丁版本）再动手；**不得**把「我理解的单位」写进文档与注释。
- **落点**：[security.md §5.2](../../standards/security.md)（供应链门禁口径）+ 本节案例；批次内已删除 exclude 并改写为 overrides 版本线。

### 2. `overrides` 是「替换解析范围」，不是「上限」

- **现象**：注释与 backlog 曾写「overrides 是解析上限而非下限」，据此推断「钉定后同线新补丁不会跟进」；实测 `^11.4.14` = `>=11.4.14 <12`、`~1.6.11` = `>=1.6.11 <1.7`，同范围补丁由常规升级正常跟进，只有跨 minor 才需人工改配置。
- **手法**：涉及 overrides 的说明统一写成「替换该包的解析范围 + 当前范围上下界 + 何时需人工推进」；M49.2a 的「上限」措辞一并订正。
- **落点**：[development.md §5.1.32/§5.1.56](../../standards/development.md) + backlog「依赖安全补丁的 overrides 钉定」条目。

### 3. 兜底动作必须先验证其副作用（Escape 会关模态弹窗）

- **现象**：视觉用例的「打开下拉面板失败 → 按 Escape 复位再点一次」兜底，在 `CaomeiDialog`（默认 `closeOnEsc: true`）内按下 Escape 会把宿主弹窗整个关掉，重试路径必然失败；同时把首次等待从 10s 压到 3s，让「慢挂载」从可通过变成硬失败。
- **手法**：设计重试 / 复位动作前，先实测该动作在**当前容器语义**下的副作用（模态内 Esc、点击遮罩、focus 转移）；重试只重复「原本要做的动作」，不做「状态归一化」式操作；首次等待不得低于原口径。
- **落点**：[testing.md §6.7](../../standards/testing.md)（兜底与反例纪律）+ `apps/platform/tests/visual/helpers/visual.ts#openSelectPanel`。

### 4. 兜底有效性要用注入式标定证明，不能只靠「连跑全绿」

- **现象**：1/6 概率的抖动下，连跑 6 轮全绿的概率约 33%，无法证明重试分支被走到；首版重试因此带着失效逻辑通过了「连跑两轮」验收。
- **手法**：对兜底类逻辑注入**目标故障**（如捕获阶段吞掉首次 `pointerdown`）后运行，断言最终成功**且耗时 ≥ 首次等待窗口**（证明首轮失败、次轮成功）；探针脚本一次性使用、跑完即删，不入库。
- **落点**：[testing.md §6.7](../../standards/testing.md)（反例验证纪律扩展）+ 本批视觉 README「反例标定记录」。

### 5. 反例标定的注入点要覆盖目标页面的主要表面 token

- **现象**：以暗色 `--caomei-color-bg-elevated` 标定设置页基线只命中 654 px（该页卡片走 `--caomei-color-bg`），余量仅 6.5×（阈值 100 px）；看起来「通过」，实际是对该 token 覆盖面积小，不是基线失敏。
- **手法**：标定选点按「页面主表面 → 文本色 → 边框」顺序取；记录差异像素与覆盖面积解释，并注明下次应改用的 token；面积异常的标定不计入「灵敏度已证明」。
- **落点**：[testing.md §6.7](../../standards/testing.md) + `apps/platform/tests/visual/README.md`「反例标定记录」。

### 6. 测试代码在 typecheck 覆盖面内，「无业务代码改动」不是免跑理由

- **现象**：`apps/platform/tsconfig.json` include `tests/**/*`，M50.4 仅改测试与文档时以「无业务代码改动」为由跳过 typecheck，掩盖了 M50.3 遗留的 `TS2349`（闭包内赋值被流分析窄化为 `null`）；审计独立复跑后判 blocker。
- **手法**：只要改动落在 typecheck 的 include 面（含 `tests/**`），就必须实跑 typecheck；闭包内给外部变量赋值时用对象持有（`{ resolve?: fn }`）绕开流分析窄化，而不是加非空断言。
- **落点**：[development.md §5.1](../../standards/development.md)（类型与验证门）+ 检查点矩阵行。

### 7. 周期任务的状态机必须有重入守卫与计数上界

- **现象**：周报插件用 `setInterval` 触发异步发送且不等待上一轮；SMTP 挂起时可跨过 15 分钟间隔并发进入，导致「单周 6 次尝试」上界被突破、`skipped_no_recipient` 幂等落库出现竞态多行。
- **手法**：周期任务用「`running` 守卫 + 状态机（终态 / 可重试 / 退避 / 上界）」显式建模；退避以上一次执行**完成时刻**为基准；配置关闭只清退避、不清计数，避免「关一下再开」绕过上界。
- **落点**：[development.md §5.1.59](../../standards/development.md)（周期任务口径）+ 检查点矩阵 5.1.59 行 + `weekly-digest-attempt.ts` + 设计稿 §6.5。

## 七十七、M51 归档批次经验沉淀（异步化关 shell / 空集合假绿 / 跳过语义 / 归一同源 / 列表次键 / 时间边界用例）

> **批次**：M51 语义与数据收口（2026-10-30，六原子 + 1 批 CI 插队）。**准入依据**：④ 工具 / 环境陷阱（`spawn` 的 `shell:true` 只按空格拼接 argv、`every()` 对空数组恒真、真实时钟边界抖动）+ ② 决策需溯源（预算跳过为什么「不交付也不回滚」、列表次键为何选主键）。落点见各条目末行。

### 1. 同步 → 异步迁移的第一步是关 shell（argv 直传）

- **现象**：交付类 git 调用从 `execFileSync` 迁到受管异步 `spawn` 后，`runTrackedCommand` 按平台默认给 Windows 走 `shell:true`（为 `.cmd` 包裹的 pnpm 设计）；Node 对 `shell:true + args[]` **不做引号化**，只按空格拼接——提交信息里的空格、`:(literal)` 路径里的括号会被 cmd 拆词（交付失败），并形成命令注入面。
- **手法**：`git.exe` 这类原生可执行文件一律显式 `shell: false`，引号化交给 libuv；只有 `.cmd` 包裹的工具链才允许 shell。迁移时逐个调用点确认二进制形态，并用「含空格 / 括号的参数往返」用例锁住，不靠平台默认值。
- **落点**：[development.md §5.1.44](../../standards/development.md)（规则扩到交付类命令 + shell 口径）+ 检查点矩阵 5.1.44 行 + `packages/engine/src/github/git-run.ts` / `git-run.test.ts`。

### 2. 空集合 `every()` 恒真：跳过 / 未验证必须显式字段

- **现象**：预算跳过终验时 `verifyProject` 返回 `[]`，下游 `actions.every(a => a.success)` 对空数组恒真 → 记为「验证通过」→ 门禁放行交付。跑得越省（预算耗尽恰在终验前）越容易出错，且报告显示全绿。
- **手法**：任何 `every` / `some` / 聚合判定都要问「空集合代表什么」；「未执行」必须与「通过」分开表达——入口回调（`onSkip`）+ 结果字段（`verificationSkipped`）+ 门禁分流三件套，空集合不得再作为通过信号。
- **落点**：[development.md §5.1.41](../../standards/development.md)（跳过不许折叠为通过）+ 检查点矩阵 5.1.41 行 + `packages/engine/src/app/repo-fix-finalize.ts` / `packages/engine/src/runners/verification-gate.ts`。

### 3. 「跳过类」与「失败类」是两回事：跳过不交付，但也不回滚、不误记失败

- **现象**：预算不足属于主动取舍，不是目标仓库失败；若按失败处理会回滚已通过验证的单元、把仓库判红；若按通过处理则交付未经完整验证的改动。两种错法都出现过（后者即上一条）。
- **手法**：跳过类审计（`BUDGET_EXHAUSTED`）不参与 exit code 与仓库失败判定；**未验证不放行交付**，但保留工作区不回滚（供人工复核）；取消另按 `ABORTED` 运行级上报，两者都不伪装成 `ENVIRONMENT_ERROR`。混合运行（预算跳过 + 真实失败）按真实失败整仓回滚。
- **落点**：[executor-process-isolation.md §8.5/§8.6](./executor-process-isolation.md)（预算接口契约与交付口径）+ [run-failure-taxonomy.md](./run-failure-taxonomy.md)（`BUDGET_EXHAUSTED` 类别与防御性映射）+ `packages/engine/src/app/budget.ts`。

### 4. 写入归一与读取解析必须同源（JSON 配置列）

- **现象**：`tags` 写入侧经 Zod trim / 去重，读取侧只过滤非字符串：同一行 `'[" prod ","prod"]'` 读回是重复且带空格的集合，而按合法输入重写会得到 `['prod']`——「写入什么 ≠ 读回什么」，UI 展示重复、按标签筛选漏命中。
- **手法**：把归一抽成纯函数作单一事实源，写入 side 用它做 transform、读取 side 用它做 parse；容量 / 上限只在写入把关，读取保持宽容（不截断存量行）；写入先去重再判容量，避免重复项白占额度。
- **落点**：[development.md §5.1.45](../../standards/development.md) + 检查点矩阵 5.1.45 行 + `apps/platform/server/utils/repository-tags.ts` / `entities/repository.ts#parseTags`。

### 5. 列表查询必须显式唯一列次键

- **现象**：`ORDER BY createdAt DESC` 在批量插入 / 同类事件同毫秒时并列，行序由数据库返回顺序决定——同一查询两次可能不同；视觉基线与 `take(500)` 截断集合随之抖动，且测试只能写「集合包含」这种弱断言。
- **手法**：主排序键可并列的列表查询统一追加唯一列（通常主键）DESC 作次键；次键只保证**确定性**，不承担业务意图顺序（意图顺序仍由 fixtures 钉死时间戳）。用例用同键多行断言「两次查询一致 + 按主键 DESC」，而不是只断言集合。
- **落点**：[api.md §4 排序确定性](../../standards/api.md)（严格约束）+ 检查点矩阵 api.md §4 行 + `apps/platform/server/api/alerts/index.get.ts` / `index.get.test.ts`。

### 6. 时间敏感用例不要拿真实时钟的「恰好等于阈值」

- **现象**：`deadlineAt = Date.now() + MIN_STEP_BUDGET_MS` 在构造时算、`budgetAllows` 的 `now` 在调用时取，间隔 ≥1ms 就把余量吃到 59999ms，全量并发下偶发失败（单文件连跑多轮才复现）。
- **手法**：优先给被测函数注入 `now`；无法注入时边界值留明确余量（阈值 + 足够大的常数），并另用显式常量断言边界（`= 阈值` 允许 / `阈值 - 1` 拒绝），不要让真实时钟充当边界。
- **落点**：[testing.md §6.14](../../standards/testing.md) + 检查点矩阵 testing §6.14 行 + `packages/engine/src/app/budget.test.ts`。

## 七十八、M52 归档批次经验沉淀（门禁口径自校验 / 取证副作用 / 契约字段落库 / 断言收敛）

> **批次**：M52 文档平价与验证收口（2026-10-31，四原子 + 4 批追加临时待办）。**准入依据**：④ 工具 / 环境陷阱（Playwright `updateSnapshots` 的写盘语义、VitePress 跨 locale 链接解析、fixtures 端点 schema 与写入映射不同源）+ ② 决策需溯源（为何把 slug 模拟器做成可自校验、为何视觉断言必须收敛到目标元素）。落点见各条目末行。

### 1. 「宽松归一化」的锚点校验等于没校验

- **现象**：`check:docs` 的 `normAnchor` 为兼容三种 slug 规则剥离了全部标点（含 `-`），于是 GitHub 口径的 `31-新需求默认走评估--backlog原则` 与 VitePress 产物 id `_3-1-…` 被判为「同一标题」——站点上点不动的死锚全部绿；实测缺口 696 处 / 97 文件，是预估的 2 倍多。
- **手法**：多渲染器兼容只能用于「是否有这个标题」的宽松判断；「能不能跳转」必须另立**精确**规则（逐字符等于产物 id），并在报错里直接给出应改成什么。两者并存：宽松规则保留历史形态的容错，精确规则负责形态正确。
- **落点**：`check-docs` 第 8 条规则 `anchor-id` + [documentation.md §2](../../standards/documentation.md)（Markdown 约定：锚点以产物 id 为准）+ 检查点矩阵 `documentation.md §2` 行。

### 2. 渲染口径的模拟器必须能被构建产物自校验

- **现象**：slug 规则靠「行正则模拟 markdown-it」实现，一旦 VitePress 升级改规则，模拟器与产物会一起错，而错的方向是「把正确写法判红」。
- **手法**：模拟器之外再留一条**以产物为权威**的校验（`docs:check:anchors` 读 dist 里的 `<h*-id>`），并把「每页推算 id 序列 == 产物 id 序列」也纳入其中；该自校验只作 warning（未覆盖的合法标题形态不应把文档判红），锚点未命中才是阻断项。
- **落点**：`scripts/docs/verify-anchor-dist.mjs` + [documentation.md §2](../../standards/documentation.md)（产物复核口径）+ `gates:docs` + 检查点矩阵 `documentation.md §2` 行。

### 3. 「重复生成 N 轮」必须验证副作用才算证据

- **现象**：用 `--update-snapshots`（不带值）连跑 10 轮记录 sha256 恒定，被判为「字节稳定」；实际该 preset 是 `changed`——**比较通过时不写盘**，10 轮读的是同一个文件。mtime 一直没变是唯一线索。
- **手法**：任何「重复生成 / 重建」的取证，先确认**副作用**是否发生（mtime 前进、字节数变化、日志写明写入），再比较产物；只比较内容而不验证写入，等于比较输入。
- **落点**：[testing.md §6.7](../../standards/testing.md) + `apps/platform/tests/visual/README.md`「运行间确定性取证」。

### 4. update 与 compare 走的是两条取帧路径

- **现象**：`toHaveScreenshot` 比对时会重试到连续两帧一致，而 `--update-snapshots` **不比对、直接落首帧**；于是「重写后的基线」经常不是「比对时的稳定帧」——`=all` 重写后立即比对，4 例失配 1218-1313 px。
- **手法**：把「稳定」前移到用例侧（连续两帧截图逐字节相同才返回），让两条路径落同一帧；上限内未收敛时告警而不是静默放行（否则 update 仍会写出非稳定帧且无从察觉）。
- **落点**：[testing.md §6.7](../../standards/testing.md) + `apps/platform/tests/visual/helpers/visual.ts`。

### 5. schema 接受 ≠ 落库：契约字段要追到写入映射与视图

- **现象**：e2e fixtures 端点的 Zod schema 允许 `attribution`，注释还写着「供视觉基线构造带标签的信号」，但写入映射逐字段重建对象时漏了这一项，fixture 类型也没声明——注入的归因静默丢失，视觉基线永远是「无标签」形态，断言看着有覆盖实际没数据。
- **手法**：新增契约字段时沿「schema → 写入映射 → 实体列 / JSON → 视图映射 → 前端渲染」逐段核对，任何一段手工重建对象都可能漏字段；fixtures 之类测试基础设施同样适用（它也是生产链路的镜像）。
- **落点**：[development.md §5.1.45](../../standards/development.md)（契约字段端到端）+ 检查点矩阵 `development.md §5.1.45` 行。

### 6. 视觉断言要收敛到目标元素，不能靠泛化选择器

- **现象**：断言 `.caomei-tag--danger` 存在时，同行另有 `state` 标签（failure → danger）与 `kind` 标签（neutral），归因色调映射改坏了断言仍然绿——只有像素基线兜底，而基线一 update 就失去判别力。
- **手法**：给被检元素加稳定 class / `data-testid`，断言「该元素 + 该属性 + 文案」三者成对；新断言必须用 mutation 验证能拦住对应回归（本案把色调 danger → warning，断言立刻失败）。
- **落点**：[testing.md §6.7](../../standards/testing.md)（视觉断言判别力）+ 检查点矩阵同项 + `platform-pages.visual.test.ts`。

### 7. 结构平价要按「身份」比，不能按「数量」比

- **现象**：中英指南只比 H2/H3 数量时，「删掉「环境变量」整节 + 加一节无关小节」仍能通过——正是这条规则要防的漂移形态。
- **手法**：跨语言无法比标题文本，就维护**显式映射表**（zh 标题 → en 标题），两侧改名都 fail-closed；数量只作为 H3 的兜底。键位（env / CLI / Action 输入）按集合比，且「取不到键位」也 fail-closed（否则表格改名即静默关掉门禁）。
- **落点**：[documentation.md §6](../../standards/documentation.md)（指南平价）+ `scripts/docs/check-guide-parity.mjs` + 检查点矩阵。

### 8. 跨 locale 的相对链接按站点路由解析，不按磁盘路径

- **现象**：`docs/i18n/en-US/design/x.md` 在站点上的路由是 `/en-US/design/x`。从 zh 页用 `../i18n/en-US/design/x.md` 指向它，磁盘路径存在（`check:docs` 绿），站点却渲染成 `/i18n/en-US/design/x` → 404；`ignoreDeadLinks: true` 把构建告警也吞了。
- **手法**：跨 locale 链接要么写站点路由可解析的相对层级（并在 dist 里实测 href 目标存在），要么改用 GitHub 外链；构建后抽查新页面的正文 href，而不是只看 `check:docs` 的磁盘存在性。
- **落点**：[documentation.md §2](../../standards/documentation.md)（跨 locale 链接条款）+ 检查点矩阵 `documentation.md §2` 行。
