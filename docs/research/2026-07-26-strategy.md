# 战略思考与方向细化

> 编制日期：2026-07-26
> 背景：在完成2026年7月竞品调研后，结合近期实践思考，对项目定位和实现路径进行重新梳理。

---

## 1. 竞品格局再确认

### 1.1 现有竞品都不在同一个生态位

| 竞品 | 核心定位 | 与我们的差异 |
|------|---------|-------------|
| **GitHub Dependabot + AI Agent** | 平台内置，按 alert 逐个处理 | 需要 Copilot 订阅（价格大幅上涨），仅限 github.com，不支持批量/自部署 |
| **Devin (Cognition AI)** | 通用 AI 软件工程师 | 修依赖更新是大材小用，$20-200+/月，不可自部署，定位过于通用 |
| **RepoWarden** | AI 维护工程师 | 强依赖 GitHub + Claude，纯托管不支持自部署，£24-1,200/月 |
| **Pixee** | Agentic AppSec（语义修复） | 不走依赖 bump 路线，专注代码级漏洞修复（SSRF/SQLi/XSS），属于不同赛道 |
| **Renovate / Dependabot Core** | 纯依赖版本升级 | 只 bump 版本，不修复代码，不处理 breaking changes |

**结论：市场上确实没有定位完全相同的产品。** 这证实了这是一个十分细分的赛道——可能也正是因为过于细分，商业回报不明朗，大公司/资本没有兴趣入场。

### 1.2 窗口期判断

GitHub Copilot 在 2026 年的价格大幅上涨，为独立工具留下了时间窗口。但如果未来 Copilot 价格回调或免费层包含 Agent 能力，本项目的 GitHub 生态位将急剧压缩。因此：

- **短期（0-12 个月）**：窗口存在，聚焦 GitHub 生态快速验证
- **中期（12-24 个月）**：必须建立跨平台能力（GitLab / 自托管），降低对 GitHub 的依赖

## 2. 问题本质的重新理解

### 2.1 维护多个项目时 Dependabot alerts 容易过载

对于维护多个项目的开发者，问题不是"单个告警很难修"，而是：

- 每个项目每周收到 3-20 个 Dependabot PR
- 其中 10-30% 存在 CI 失败（breaking change / lockfile 不一致 / 类型变更）
- 每个失败需要 30-120 分钟排查修复
- 项目数 × 告警数 = 海量重复劳动

**核心矛盾**：每个告警单独看都很简单，但数量堆积后就变成沉重的维护负担。

### 2.2 类似的错误有相同的解法

在实际维护中会发现，很多 breaking change 是有规律的：

| 错误类型 | 典型场景 | 修复模式 |
|---------|---------|---------|
| TypeScript 类型变更 | 包导出路径改变、类型重命名 | 更新 import 路径 / 替换类型名 |
| API 签名变更 | 函数参数变化、返回类型改变 | 调整调用处参数 |
| 包合并/拆分 | 多个包合并为一个 | 更新 import + 安装新包 |
| 配置格式变更 | ESLint/TypeScript 配置变化 | 迁移配置格式 |
| Lockfile 不一致 | pnpm 版本变更、间接依赖解析变化 | 固定工具链 + 重建 lockfile |
| Node 版本要求提升 | 包要求 Node >= 20 | 更新 engines 字段 / CI 配置 |

**这意味着：很多修复是可以模板化的，不需要每次都用 AI 从头分析。**

### 2.3 升级依赖的流程是固定的

依赖升级的核心流程几乎不变：

```
接收告警 → 识别受影响包 → 确定目标版本 → 执行升级
→ 运行 CI → CI 失败 → 分析失败原因 → 修复 → 验证 → 提交
```

这个流程中的每一步都是可以标准化的。AI 的真正价值不在于"替代整个流程"，而在于：

1. **分析失败原因**（读取 CI 日志，理解哪里出了问题）
2. **生成修复代码**（在已知修复模式中匹配合适的模板，或生成新的）

## 3. 核心策略转变：经验提取与复用

### 3.1 当前做法的问题

如果每次修复都让 AI 从头分析 changelog、理解代码、生成修复，存在几个问题：

- **成本高**：每次都要消耗大量 Token
- **质量不稳定**：AI 对不熟悉的项目上下文可能产生幻觉
- **不积累**：这次修复的经验无法用于下一次同样的场景

### 3.2 新的思路：AI 提取可复用的经验

```
修复流程不再是：
  告警 → AI 分析 → AI 修复 → 结束

而应该是：
  告警 → AI 分析 → AI 修复 → 从中提取修复经验/脚本 → 存入知识库
  ↓
  下次同类告警 → 先查知识库 → 匹配到已有经验 → 执行已知修复脚本
                                    ↓
                               (没有匹配) → AI 分析 → 修复 → 提取经验
```

**这背后的核心变化**：AI 不再只是"修复执行者"，更是"经验提取者"。

### 3.3 经验提取的具体形式

可复用的经验可以表现为多种形式：

| 形式 | 示例 | 适用场景 |
|------|------|---------|
| **Codemod 脚本** | `jscodeshift` transform | TypeScript/JavaScript 代码迁移 |
| **sed/regex 替换** | 全局替换 import 路径 | 包路径变更 |
| **配置迁移脚本** | ESLint 配置转换 | 配置格式变更 |
| **pnpm overrides/patch** | 锁定某个依赖版本 | 暂时不兼容 |
| **Git 补丁文件** | 完整的文件变更 patch | 复杂修复 |
| **自然语言描述** | "这个包的 createClient API 移到了子模块" | AI 下次可直接用此描述指导修复 |

### 3.4 经验的共享与演进

- **项目级复用**：同一项目多次遇到同类问题，自动匹配历史经验
- **跨项目复用**：不同项目遇到相同包的相同升级，共享经验
- **社区共享**：可选的公共经验库（类似 Renovate 的 preset 机制）

## 4. 供应链安全考量

### 4.1 问题背景

Dependabot/Renovate 默认假设"最新版本 = 最安全版本"。但现实中：

- **2024 年 axios 事件**：流行的 npm 包 axios 被攻击者盗取维护者账号，发布包含恶意代码的新版本
- **typosquatting 攻击**：恶意包使用与流行包相似的名字
- **依赖劫持**：长期未维护的包被攻击者接管后发布恶意版本

这种情况下，盲目升级到最新版本反而可能引入安全风险。

### 4.2 缓解策略

| 策略 | 说明 | 实现方式 |
|------|------|---------|
| **版本发布日期检查** | 避免升级到过于"新鲜"的版本 | `pnpm minimumReleaseAge`（pnpm 已内置） |
| **版本下载量/活跃度检查** | 异常低下载量的版本可能是恶意发布 | npm download stats API |
| **Diff 分析** | 检查新旧版本的代码差异，发现异常变更 | `npm diff` 或 registry API |
| **沙箱执行** | 在隔离环境中运行安装和测试，防止恶意代码影响宿主机 | Docker 容器 / 临时工作目录 |
| **包签名验证** | 验证包发布的签名信息 | npm 签名验证（需包作者支持） |

### 4.3 pnpm minimumReleaseAge 的意义

pnpm 在 2026 年引入的 [`minimumReleaseAge`](https://pnpm.io/package.json#pnpmauditconfigminimumreleaseage) 配置，允许指定"新版本发布后至少等待 N 天再升级"。这提供了一个重要信号：**即使是包管理器本身，也在关注供应链安全的时间维度**。

这对本项目的意义：
- 在自动升级决策中，加入"版本发布时间"作为过滤条件
- 对过新的版本（< N 天），暂缓升级并记录原因
- 在报告中标注"该版本发布于 X 天前，建议等待"

## 5. 执行策略：逐项目跑，但经验共享

### 5.1 为什么一次跑太多项目效果差

实践发现，同时让 AI 处理多个项目的修复会导致：

- **上下文丢失**：AI 在多个项目间切换，对每个项目的理解深度下降
- **修复质量参差不齐**：有些项目修复好，有些跑偏
- **互相干扰**：一个项目的失败可能影响整体的判断

### 5.2 建议的执行模式

```
┌─ 任务队列 ──────────────────────────────────┐
│  [项目 A] → [项目 B] → [项目 C] → ...         │
│  逐个执行，每个项目独立工作目录、独立上下文        │
└──────────────────────────────────────────────┘
                    │
                    ▼
         ┌─ 执行单元（每项目） ──┐
         │ 拉取告警 → 过滤       │
         │ 查历史经验库          │ ← 跨项目共享
         │ 执行修复 → 验证        │
         │ 提取新经验 → 存入知识库 │ → 跨项目共享
         │ 生成报告               │
         └──────────────────────┘
```

**执行粒度**：每个项目独立跑，但经验知识库是跨项目共享的。

### 5.3 并发控制

虽然逐项目执行，但可以通过有限并发提升效率：

- 默认并发数：2-3 个项目同时执行
- 每个项目独占一个工作目录
- 经验库是共享的（写入需要加锁）

## 6. 定位重申

### 6.1 一句话定位

> **"针对多项目维护者，自动化处理 Dependabot / Code Scanning 告警中那些简单、重复、但数量庞大的修复工作。"**

### 6.2 做什么、不做什么

| 做 | 不做 |
|---|------|
| 自动拉取 Dependabot / Code Scanning alerts | 不做通用的 SAST/DAST 扫描 |
| 自动升级依赖版本并修复 lockfile | 不承诺修复所有安全漏洞 |
| 自动处理 breaking change（AI 研判 + 修复） | 不做 Devin 那样的通用 AI 工程师 |
| 从修复中提取可复用的经验/脚本 | 不做 codemod 通用平台 |
| 逐项目执行，但跨项目共享经验 | 不建议一次跑太多项目 |
| 检查包来源安全（发布时间、diff） | 不做完整的供应链安全平台 |
| 沙箱中执行安装和验证 | 不在宿主机直接运行不受信任的包 |

### 6.3 价值主张

> **"与其每天花 30 分钟处理一个项目的 Dependabot 告警，不如用这个工具自动跑一遍，然后 review 结果。"**

## 7. 对现有设计文档的影响

### 7.1 需要对 plan.md 进行的补充

- **经验库设计**：新增"修复经验提取与存储"模块
- **供应链安全检查**：在依赖升级流程中加入版本时效性检查
- **执行策略**：明确"逐项目执行，经验共享"模式
- **沙箱执行**：在验证执行器中加入容器化运行支持

### 7.2 优先级调整建议

| 原优先级 | 调整 | 理由 |
|---------|------|------|
| AI Breaking Change 研判（Milestone 5） | 保持 P1 | 这是核心差异化能力 |
| 经验提取与复用 | **新增 P1** | 降低成本、提升质量的关键 |
| 供应链安全检查 | **新增 P2** | 重要但可在 MVP 后补充 |
| 多仓库批量（Milestone 4） | 调整为 P2 | 逐项目执行模式降低了对多仓库并发的需求 |
| Code Scanning 扩展 | 保持 P1 | 核心能力覆盖 |

## 8. 总结

经过竞品调研和实践反思，项目的核心认知更新如下：

1. **市场定位确认**：无直接竞品，是利基市场，可能盈利空间有限
2. **GitHub Copilot 涨价** = 短期窗口，长期必须跨平台
3. **AI 的角色**：不只是一次性修复，更是**经验的提取者**——从每次修复中沉淀可复用的脚本和知识
4. **供应链安全**：不能默认"最新=最安全"，需要加入发布时间检查、diff 分析和沙箱执行
5. **执行模式**：逐项目跑，经验共享——质量优于数量
6. **核心价值**：解决的是"简单但数量多"的问题，而不是"复杂但次数少"的问题
