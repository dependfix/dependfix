# 项目规划与评估规范

## 1. 规划约束

### 1.1 硬性约束

- **阶段性聚焦**：单个迭代核心任务控制在 5-6 项以内，超出时遵循「进一出一」原则。
- **功能解耦**：新功能不破坏现有核心逻辑；涉及核心架构变动必须先技术预研并更新设计文档。
- **测试先行**：规划任务时同步制定测试方案；不包含测试补全计划的功能不具备准入资格。
- **验收标准具体化**：待办条目必须写清执行范围、非目标、可验证验收标准、最小验证矩阵 / 证据落点与必要时的回滚边界；禁止「优化一下」「先做最小版本」等模糊口径。
- **任务粒度约束**：规划时预估单条任务的 diff 规模（文件数 × 行数）；预计新增 > 10 个文件或 > 800 行（新领域 / 跨模块骨架任务从严，> 5 文件即考虑拆分）时**必须拆分为可独立提交的子任务**，每个子任务有独立验收点与提交批次；禁止「一个原子条目 = 一个巨型 diff」。**本条是任务粒度约束的唯一权威声明**——其他文档（git.md、ai-collaboration.md、skill / agent 定义）仅作一行引用，不得重复抄写阈值或问题结论；合规核验由 review 阶段执行（见 code-reviewer 检查点与 Code Auditor 必查项）。
- **迭代范围与候选组合**：单次迭代核心任务应在 5-6 项以内；当上一阶段闭环后仅剩单一候选时**主动扩展**——从 backlog 挑选 UX 痛点 / 技术债 / 能力扩展类候选填充至 5 项左右；**类型平衡建议**：用户体验 ≥ 2 + 技术债 ≥ 1 + 能力扩展 ≥ 1 + 测试覆盖 ≥ 1，避免单一类型堆叠。
- **backlog 历史指针压缩**：每个阶段归档完成后必须执行 backlog 历史指针压缩——已闭环条目不再展开细节，仅保留最近 3-4 个阶段 + 早期间接指针；避免 backlog 随阶段线性膨胀；**禁止**在 backlog 中复制 `todo-archive.md` 已闭环条目的子任务细节。
- **设计先行闸门**：涉及新模块、跨模块边界调整、数据 / 接口契约重写时，先完成设计文档再进入实现。
- **阶段切换闸门**：当前阶段归档未完成前，禁止在 roadmap 中开启下一阶段的正式规划。
- **跨文档内部一致性**：「新需求处理原则」+「插队例外清单 3 类」+「合规核验 code-auditor 主责边界必查项」三段必须在 `AGENTS.md §新需求处理原则` + `ai-collaboration.md §2.1.1 新需求总原则` + `planning.md §3.1` 三处保持一致。**修复模式**：(a) 改前先 `rg -n "新需求.*处理原则" docs/standards/ AGENTS.md` 核对所有相关描述；(b) 改后 `pnpm run check:docs` 验证链接 + `rg -n` 交叉验证措辞一致；(c) 关键原则必须三处同步 + commit message 显式说明。
- **迭代内新增事项闸门**：开发 / 测试 / 审计过程中发现的额外事项默认不自动并入当前阶段——① 先核对是否已在 `todo.md` / `roadmap.md` 当前阶段或 `todo-archive.md` 中；② 不在规划内先完成快速分流（阻塞 / 高风险 → 插队，其他 → 延期）；③ 未完成判定前严禁直接进入开发。

## 2. 路线图与待办管理

### 2.1 路线图

- `docs/plan/roadmap.md` 维护阶段概览（每阶段含目标、优先级、状态）；已完成阶段标注为「已审计归档」或等价状态；下一阶段在上一阶段归档完成后才开启正式规划；详细任务不在 roadmap 重复展开，以 `todo.md` / `backlog.md` 为准。

### 2.2 待办事项

- `docs/plan/todo.md` 仅包含当前阶段的具体实施任务，任务按里程碑分组；状态标记 `[ ]` 待办 / `[x]` 已完成 / `[-]` 已取消。
- 每条子任务（子阶段条目）必须含 8 要素，缺一项视为模糊口径必须退回补齐——见 [§2.5](#25-任务详细度要求)。

### 2.3 待办积压

- `docs/plan/backlog.md` 存放后续阶段的详细任务，区分两类：**长期主线任务**（可跨阶段保留，记录最近一次上收阶段、当前状态与下一切片方向）与**短期 / 一次性候选**（上收后去重，不得同时出现在当前规划与 backlog 中）。
- **候选上收 / 关闭后的同步动作**：从 backlog 移除候选后，其**父段标题括号内的枚举**会 stale，必须同步收敛标题与正文；同时清理**已失效候选**（实现对象已被其他阶段闭环），按 [§4.4 第 11 条](#44-大批量归档批次操作规范)「完全闭环 → 删除」处置。

### 2.4 归档管理

- 阶段完成后详细内容从 `todo.md` 移入 `docs/plan/todo-archive.md`，保留原始层级结构、状态与验收标准以确保可追溯。
- **阶段归档完成后必须从 `backlog.md` / `todo.md` 清出所有「已闭环 / 已归档」内容**（归档摘要 / 闭环整理 / 已闭环批次指针 / 已落地动作详细描述）；**长期主线任务章节下面有且仅有「可多阶段反复执行」的任务**；已闭环内容统一由 `todo-archive.md` 主窗口 + `archive/todo-archive-phases-*.md` 分片维护（操作规范见 §4.4 第 11 条）。

### 2.5 任务详细度要求

`todo.md` 与 `todo-archive.md` 的每条子任务（子阶段条目）**必须**包含以下 8 要素，缺一项视为模糊口径必须退回补齐：

1. **目标**：要达成什么（一句话可证伪，避免口号式描述）
2. **优先级**：P1 / P2 / P3（与 backlog 主条目 P 编号一致）
3. **范围**：包含什么（具体文件 / 模块 / 子模块路径，避免抽象范围）
4. **验收标准**：可证伪的具体条款（checklist 形式，≥ 3 条；含命令 / 阈值 / 期望输出）
5. **不做什么**：边界（明确排除项，避免 scope creep）
6. **依赖**：前置任务 / 触发条件 / 关联 backlog 条目（引用具体 commit / PR / 文档段）
7. **交付物**：commits 数量 + files 清单 + 文档（每条预期 commit 的文件级 impact）
8. **风险与缓解措施**：潜在风险点 + 缓解方案（≥ 1 条，避免空洞描述）

**量化断言可复现口径（hard requirement）**：条目中的统计数字（扫描命中数、文件数、覆盖率、行数等）必须写「量级区间 + 每个值标注测量方（执行角色 / 审计方）+ 可复现命令或脚本」，禁止只写单一精确值而无口径。新增含统计数字的候选时先自问「第三方能否仅凭条目内信息复现该数字？」。

**跨文档量化口径同源区分（hard requirement）**：同一批需求在多个文档（`todo.md` / `roadmap.md` / `backlog.md` / `todo-archive.md` / `archive/index.md`）之间引用时，必须区分「用户报告项数」「登记候选数」「上收原子数」等不同计数并给出换算关系，不得让同一批次在不同文档出现互相矛盾的数字。

**禁止模糊口径**（按 [§1.1 验收标准具体化](#11-硬性约束) 扩展）：「优化一下」/「清理一下」/「增强一下」；「先做最小版本」/「做个基础版」/「做个简化版」；「顺手做」/「一起处理」/「顺便改」；「后续完善」/「持续优化」/「视情况」；仅 1-2 行描述的子任务清单（信息密度不足以指导实施）。

**条目格式示例**：反例为 `- **M.x.1**（P2）Code Scanning RG-W01 修复 —— 来源：audit`（信息密度不足）；正例为 8 要素齐全的完整条目（目标 / 范围含 `file:line` / ≥ 3 条可验证验收标准 / 不做什么 / 依赖 / 交付物 / 风险与缓解），完整样例见 [归档 M19-M21 分片 §M21.1](../plan/archive/todo-archive-phases-m19-m21.md)。

**合规核验**：本条由 review 阶段执行，详见 [code-reviewer skill](../../.github/skills/code-reviewer/SKILL.md) + [code-quality-checklist §todo.md 子任务详细度审计](../../.github/skills/code-reviewer/references/code-quality-checklist.md) + Code Auditor 主责边界「todo.md 子任务详细度审计」。

## 3. 迭代中途新增事项分流

1. **范围核对**：先检查是否已在 `todo.md` / `roadmap.md` 当前阶段或 `todo-archive.md` 中。
2. **分类决策**：**A 类（当前范围内）**——仅补足当前验收标准的配套工作 → 继续执行并补充说明；**B 类（允许插队）**——**仅限**直接影响可用性的生产事故 + 安全漏洞（详见 §3.1 例外清单）→ 写入 `todo.md`，标注插队原因 + 用户明确授权；**C 类（延期）**——体验优化、非阻塞重构、探索性想法、未来功能 → 写入 `backlog.md`。
3. **容量控制**：B 类事项进入后若超出 5-6 项，须挪出一项低优先级内容至 `backlog.md`。
4. **禁止静默膨胀**：不得在未告知用户的情况下把原子任务扩展成新的功能包。

### 3.1 新需求默认走"评估 → backlog"原则（hard requirement）

**核心规则**：**新需求**（新功能 / 新模块 / 新集成）的默认处理路径是**先评估（P 阶段规划 + requirement-analyst 需求澄清）→ 进入 backlog.md §短期候选 → 等待用户明确决策阶段 → 经用户授权后从 backlog 上收至 `todo.md` §当前阶段**；**不直接升级为下一阶段 todo.md §Mxx**（未经用户明确授权，backlog 候选不得自动获得阶段编号）；**不默认优先级排序**（候选池按「类型平衡」原则选取是用户决策行为，不是 AI 默认推断）。

**插队例外清单**（仅以下 3 类可直接写入 `todo.md` 当前阶段并分配阶段编号）：

1. **安全问题**：已确认的安全漏洞（Code Scanning 告警、Snyk / Dependabot critical 漏洞、有 PoC 的安全 issue）。
2. **漏洞问题**：依赖链中高危漏洞（critical CVE、GHSA 标识为 critical / high 且影响 dependfix 自身或被 dependfix 管理的仓库）。
3. **直接影响可用性的任务**：生产环境故障、P0 / P1 事故恢复、CI 主链路（lint / typecheck / test / build）阻塞、用户报告的 blocker 级功能缺失。

**例外清单外的全部需求**（功能增强、体验优化、代码重构、新模块、依赖升级、监控 / 告警增强等）→ **必须先评估后入 backlog**，不得直接写入 `todo.md` 当前阶段。

**评估标准**（[requirement-analyst skill](../../.github/skills/requirement-analyst/SKILL.md) 五要素）：目标（业务价值 + 真实需求 vs 表面需求）/ 边界（in-scope / out-of-scope）/ 验收标准（具体可测）/ 优先级（与 backlog 候选池对比）/ 风险与依赖。评估完成后形成 [backlog.md §短期候选](../plan/backlog.md#短期--一次性候选任务上收后去重) 条目（含 8 要素，见 [§2.5](#25-任务详细度要求)）。

**典型反模式**（AI 单方面违规）：主动将 backlog 候选写为 `todo.md §M23.1` 等带阶段编号条目；推断「本批次最高优先级是 X」并默认启动；用户提出需求后不经评估直接进入 D 阶段；候选因「看起来很重要」被跨过用户决策直接落地。

**合规核验**：本条由 [code-auditor 主责边界「新需求未默认升级为下一阶段 todo」必查项](../../.github/agents/code-auditor.agent.md) 强制检查——改动涉及新增功能需求但未走 backlog → Reject 退回。

### 3.4 阶段启动决策前置交叉核验硬要求（M27.1 重复评估问题 / 2026-09-10）

**核心规则**：当 `todo.md` §当前阶段新增条目（无论 backlog 候选上收 / 插队例外 / 用户直接决策），**必须**执行以下三重交叉核验，**未通过任何一项**不得进入 D 阶段：

1. **todo-archive.md 历史阶段表格核验**：`rg -n "已闭环|不计入本批|不计入 M\d+|ahead=0.*已推" docs/plan/todo-archive.md docs/plan/archive/todo-archive-phases-*.md` 扫描最近 3-5 个阶段表格，验证候选对应 backlog 条目的子任务是否已 ahead=0 闭环；发现「已闭环」标注必须从任务段删除对应范围。
2. **git log 历史核验**：`git log --oneline -- <候选相关路径>` + `git log --all --grep="<候选标识>"` 验证候选对应 commit 是否已 ahead=0 推 origin/master；已推则从任务段删除对应范围。**标注历史 commit 的「C 编号 / M 阶段」时不能凭同域描述推断**，必须 `git show --stat <hash>` + 归档分片核实归属。
3. **实际代码侧 anchor 核对**：打开候选相关代码文件，验证候选描述的状态与实际代码一致；发现已实现则从任务段删除对应范围。

**触发条件**：`todo.md` 当前阶段 banner 修改（新增阶段）；新增 `M\d+\.\d+` 原子条目；任务段范围 / 验收标准 / 交付物修改。

**典型反模式**（M27.1 重复评估问题）：仅读 backlog.md / todo-archive.md 文档侧资料而未打开实际代码验证；决策描述中出现「参考 NNN 实施」自相矛盾却未先厘清（NNN 仅「参考实施」则候选未落地、已 100% 落地则候选不需增强）；决策 D 阶段前未用 `git log --oneline -- <相关路径>` 做 5 分钟核对。

**合规核验**：本条由 [code-auditor 主责边界「阶段启动重复评估自检」必查项](../../.github/agents/code-auditor.agent.md) 强制检查——commit 涉及 `todo.md` 当前阶段新增 / 修改时，三项交叉核验任意一项未执行 / 未通过 → Reject 退回。

**backlog 描述同步要求**：新增条目对应 backlog 候选时必须同步修订 backlog.md——(a) 已 ahead=0 闭环的子任务追加 ✅ 标注 + commit hash 回填；(b) 暂缓的子任务追加 ⏸️ 标注 + 原因；(c) 「保留为后续增强候选」措辞必须基于「当前未落地」前提，否则删除。

## 4. 阶段归档流程

### 4.1 归档准入

- 确认当前阶段核心条目全部完成；「进行中」「待继续观察」类描述先判断是阻塞归档还是仅属运行期观察；若缺少 `todo.md` 清理、回归记录、阶段总结或 `todo-archive.md` 归档块 → 视仍在收口中。

### 4.2 文件更新顺序

- ① 先清理 `todo.md`（移除已完成阶段正文）；② 再追加 `todo-archive.md`（完整归档块：审计结论、验收摘要）；③ 最后同步 `roadmap.md`（阶段状态改为「已完成」或「已审计归档」）。

### 4.3 最低验证

- `todo.md` 已清理 + `todo-archive.md` 已追加 + `roadmap.md` 已同步阶段状态；质量门结论可查（lint + typecheck + 定向测试）；Review Gate 有 `Pass` / `Reject` 结论。
- **Session Wisdom 蒸馏检查**：若 `.session/wisdom.md` 活跃条目 >= 20（`pnpm distill:wisdom --check`），执行一次蒸馏（见 [Session Wisdom 蒸馏机制](../design/governance/session-wisdom-distillation.md)）。
- **用户可见文档同步**：里程碑收口时除 todo / roadmap 外，还需同步 `docs/index.md` 当前状态、guide 文档与设计文档中的「规划中」标记。

### 4.4 大批量归档批次操作规范

涉及跨文件 markdown 链接修改 / 段标题重命名 / 段删除时，必须遵守以下操作规范：

1. **anchor 核对**：写 markdown 链接前必须 `rg -n "^## " <目标文件>` 确认锚点真实形式（括号转 anchor 规则不是直觉）；check:docs 是兜底而非首选。
2. **跨文件外链主动追踪**：段删除 / 段重命名前必须 `rg -n "<删除段标题>"` 全仓库扫描所有外链，列出每个外链文件 + 位置 + 目标并逐个修复为新的归档位置。
3. **跨目录相对路径精确**：`docs/<dir1>/` 引用 `docs/<dir2>/` 需 `../<dir2>/`，多级按 `../../` 累加，写之前主动计算。**批量替换相对路径前缀时** old 片段必须**从路径字符（`../`）起写、不要带上 `](`**——带上会把 `]` 一并替换掉令链接退化为纯文本；改完立即做 **malformed 检测**复核（`rg -n "\[[^]\n]*\((\.\.?/|/)"` 应 0 命中）并人工确认 `](` 与 `)` 成对（自建链接校验器对坏语法静默跳过，不能作为唯一证据）。
4. **commit 分组追踪**：归档文案分组 commit 时必须**先列每个 commit 归属**，避免子批次 commit 与收口 commit 重复计数。
5. **ahead commits 核验 + 动态描述**：归档文案的 ahead 数必须用 `git rev-list HEAD ^origin/master --count` 双向核验，不能凭印象估算。**额外约束**：ahead 数字写具体值极易过时，改用 commits 列表 + 核验命令（与 [AI 协作规范 §2.P.1](./ai-collaboration.md#p1-ahead-状态动态描述原则避免-staleness) 配套）。
6. **段结构引用原则**：已删除段不在外链保留，外链改为指向新归档位置 + 段标题对齐（避免渲染降级到文件顶部）。
7. **死链验证**：归档后必须 `pnpm run check:docs` 核验 0 error；CI Test job 跳过盲区需在归档批次前主动跑通。
8. **算式校对（commit 数量 + 子任务数量去重统计）**：归档文案中「X 子任务 / Y commits」等算式信息**必须从 git log first-parent 列表去重统计**（`git log master --first-parent --oneline <范围> | grep -E "<子任务前缀>" | sort -u | wc -l`），不依赖估算；子任务数量按编号列表一一对应。
9. **区分已归档内容与必要信息**：清理 `backlog.md` / `todo.md` 时必须区分——**可删除**（`闭环整理` 这类已归档内容）；**必须保留**（`维护规则`、`长期主线任务详细描述`、`未上收待办项`、`待人工验收条目`）。**判断标准**：删除前问「这个信息在下一阶段启动时是否需要？」；归档后 `pnpm run check:docs` 检查断链。
10. **预防性迁出后 cross-reference 更新**：todo-archive.md 预防性迁出主窗口内的 § 至分片后，其他文档中所有引用已迁出 § 的锚点全部失效，必须统一更新——用 `rg -n "todo-archive.md#m\d+-|<被迁出§标题>"` 全仓库检索；锚点格式注意 `--`（双连字符）在 check-docs 中自动转换为单词连续，不要手动拼接；统一指向分片文件路径，不保留主窗口引用；更新后 `pnpm run check:docs` 核验 0 error。
11. **归档后 backlog.md / todo.md 必清理（必执行项）**：阶段归档完成后必须清出所有「已闭环 / 已归档」内容——删除 backlog 的历史归档指针段 / 已迁移沉淀段 / 已评估不实现段 / 批次上收与归档摘要 blockquote / 主线任务章节下的已闭环批次记录 / 短期候选中已闭环条目 / todo.md 的完成摘要段与「下一阶段规划」段、「待人工验收」段（属 backlog 范畴）。**必须保留**：维护规则、长期主线任务（仅多阶段反复可执行）、周期性回归验证层、短期候选中未闭环条目、延期暂缓项、待人工验收、已知边界与 known-issue。**边界**：区块定义 / 维护规则类 blockquote 属必要信息，不属删除对象。**判断标准**：删除前问「下一阶段启动时是否需要？」；本规则与第 9 条（反向防「删过头」）配套执行。
   - **§已知边界段 / 长期主线段 stale 描述处理指引**：不应仅做「保留 / 删除」二元决策，部分闭环时必须**更新描述**——**完全闭环**整段删除；**完全未闭环**保留原描述；**部分闭环**更新描述 + 引用闭环 commit hash；**场景变更**更新描述；**长期主线卡闭环同步**（验收条件达成 / 目标被某阶段闭环时必须整卡删除或改写状态，不得保留 stale 的「暂停 / 观察中」）。**触发条件**：任意阶段 commit 涉及 backlog §已知边界段 / 长期主线段候选的闭环判定或场景变更；Mxx 归档批次涉及该两段清理。**合规核验**：由 [code-auditor 主责边界必查项](../../.github/agents/code-auditor.agent.md) 强制检查，五项判定任意一项未执行 / 未通过 → Reject 退回。
12. **超长行完整性校验**：写入超长 markdown 行（如 `archive/index.md` §5 批次登记表行）时**禁止直接粘贴被截断的工具输出**；写入后必须校验——`rg -n 'line truncated' docs/plan/` 零命中 + 表格行首尾 `|` 成对 + 单元格内 `|` 已转义 + 无重复行 / 游离分隔符。
13. **口径同步复扫必须用结构化查询**：跨文件同步某「事实性口径」（默认命令链、默认配置、阈值等）后，复扫若只搜上一轮表述的**字面 pattern** 会漏掉措辞变体（逐命令反引号、简写、双语镜像）造成同章节自相矛盾。**正确做法**：以语义站点清单 + 结构化查询（如 `rg lint | rg build | rg -v test`）枚举候选，再人工过滤历史 / 动机性引用；双语镜像须单独扫。
14. **已知边界条目闭环时的 archive 基线跨文件同步**：`backlog.md` 的已知边界条目闭环时，**除 backlog 整段删除外**还必须同步 `docs/plan/archive/index.md` §4——①「保留」清单中的该条目；② §4 正文中对它的前向描述。**做法**：闭环 commit 前用 `rg -n "<条目简称>" docs/plan/archive/index.md` 确认全部落点。
15. **执行期发现「范围外同源陈旧」的处置路径**：原子条目执行中发现 AC 范围外的**同类陈旧 / 同构遗漏**时按三步走——① 带 `file:line` 证据**提请用户决策**（不自行扩范围）；② 用户授权后一并同步并在条目「范围」段与本批 commit 说明中显式记录授权来源；③ AC 明确排除的部分**不动**，但必须**登记候选**（无阶段编号）且登记位置要与该区块定义自洽。**配套**：老旧指针复扫面须覆盖源码注释（`packages/**/*.ts` + `scripts/**/*.mjs`），不能只扫 `docs/` + `.github/` + `apps/`（`scripts/` 与 `archive/` 均在 `check:docs` 覆盖面之外，须人工复扫）。

> 本节为大批量文档归档批次（multi-file edit + 段结构变更）的统一操作规范；其他文档归档 / 小批量编辑仅执行相关条目。

## 5. 需求采访与意图抽离

针对模糊需求，必须先通过「采访」方式反问用户：先结构后细节、一步步递进；一次一个问题、待用户回答后再追问；目标是抽离出最核心、最真实的业务需求；**在核心需求未对齐前严禁进入开发阶段**。
