# auto-fix-github-security 实施任务清单

## 1. 文档定位

- 文档类型：实施任务清单。
- 目标读者：项目维护者、实现角色、后续拆分 issue 的执行者。
- 文档目标：把 [docs/plan.md](docs/plan.md) 中的设计方案拆成可排期、可验收、可继续细化的任务列表。

## 2. 使用说明

- 优先级说明：`P0` 表示首期必须完成，`P1` 表示第二阶段重点，`P2` 表示增强项。
- 状态建议：`未开始`、`进行中`、`阻塞`、`已完成`。
- 拆分原则：一个任务应对应一个明确交付物，避免把多个能力打包成一个不可追踪的大任务。

## 3. 里程碑总览

### Milestone 0: 基线收敛

目标：把项目从模板状态收敛到可承载自动化方案的基础形态。

### Milestone 1: MVP 单仓库自动修复

目标：跑通单仓库、Node.js / pnpm 生态下的 Dependabot 告警拉取、过滤、修复、验证和报告。

### Milestone 2: GitHub Action 接入

目标：把 MVP 能力接入 GitHub Actions，支持定时或手动运行。

### Milestone 3: Code Scanning 扩展

目标：接入 Code Scanning 告警并引入规则分级处理。

### Milestone 4: 多仓库治理增强

目标：支持多仓库批量执行、限流、策略增强和长期报告归档。

## 4. 实施任务列表

## 4.1 Milestone 0: 基线收敛

### T001 建立项目骨架

- 优先级：`P0`
- 依赖：无
- 交付物：按方案拆出的目录结构与最小入口代码。
- 任务内容：
  - [ ] 新增 CLI 入口目录。
  - [ ] 新增配置层、GitHub 集成层、核心域层、修复器目录。
  - [ ] 新增统一日志与错误模型基础设施。
- 完成定义：
  - [ ] 项目结构与 [docs/plan.md](docs/plan.md) 的建议目录基本对齐。
  - [ ] `pnpm run build` 可通过。

### T002 定义核心配置模型

- 优先级：`P0`
- 依赖：T001
- 交付物：配置类型、默认配置、环境变量读取逻辑。
- 任务内容：
  - [ ] 定义运行模式、严重级别阈值、仓库列表、dry-run、是否创建 PR 等配置项。
  - [ ] 支持环境变量与 CLI 参数合并。
  - [ ] 给出默认值与校验错误提示。
- 完成定义：
  - [ ] 本地运行时能解析一份完整配置。
  - [ ] 缺失关键配置时能输出可读错误。

### T003 固定工具链策略

- 优先级：`P0`
- 依赖：T001
- 交付物：Node / pnpm 版本策略文档与代码实现约束。
- 任务内容：
  - [ ] 定义运行时 Node 与 pnpm 版本来源优先级。
  - [ ] 明确禁止在自动修复链路中直接使用漂移型 `latest`。
  - [ ] 设计 lockfile 修复前后的工具链记录字段。
- 完成定义：
  - [ ] 后续执行器能读取确定版本配置。
  - [ ] 文档和实现不再依赖不稳定的默认版本推断。

### T004 定义标准告警模型

- 优先级：`P0`
- 依赖：T001
- 交付物：统一的 `NormalizedSecurityAlert` 类型与转换接口。
- 任务内容：
  - [ ] 定义 Dependabot 与 Code Scanning 的共同字段。
  - [ ] 定义严重级别映射。
  - [ ] 定义 fixable、fixStrategy、recommendedVersion 等扩展字段。
- 完成定义：
  - [ ] 任一数据源进入过滤层前都能转换为统一模型。

## 6. 建议执行顺序

建议先按以下顺序推进：

1. T001 → T004，先完成骨架、配置、工具链、模型。
2. T101 → T109，先做 MVP 单仓库闭环。
3. T901 → T903，与 MVP 并行补齐测试和审计能力。
4. T201 → T204，把 MVP 接入 GitHub Actions。
5. T301 → T304，再扩展 Code Scanning。
6. T401 → T404，最后做多仓库治理增强。

## 7. MVP 完成判定

满足以下条件时，可以认为首期 MVP 达成：

- [ ] 能手动指定一个仓库执行任务。
- [ ] 能拉取 Dependabot alerts 并完成严重级别过滤。
- [ ] 能对可升级依赖执行自动修复。
- [ ] 能处理典型 `pnpm i --frozen-lockfile` 漂移错误。
- [ ] 能执行最小验证并输出成功或失败原因。
- [ ] 能生成 Markdown 和 JSON 报告。
- [ ] 本地命令链路可稳定复现。

## 8. 后续拆分建议

当准备进入开发阶段时，建议把每个 `Txxx` 任务进一步拆成 issue，并至少补齐以下字段：

- 负责人
- 预计工期
- 风险说明
- 验收用例
- 是否阻塞其他任务

这样可以避免实施阶段再次回到模糊需求状态。
